# App leftovers

`AppLeftoversView()` is an explicit, review-only scan for app data left outside the normal uninstall flow. It never registers a Smart Care module. The Uninstaller can present this page through its Leftovers entry.

The scan inventories Preferences, Application Support, Caches, Containers, Group Containers, Saved Application State and Application Scripts in the current user's Library. Application bundles under the system and user Applications directories, system app directories, installed Homebrew cask app artifacts, running bundle identifiers and existing Launch Services registrations retain matching owners. Nested app folders are inspected; inaccessible, malformed, linked or over-budget application inventories cannot prove absence. Exact installed display names are also omitted from uncertain findings.

A reverse-DNS filename alone does not establish that a deleted app owned a path. An ordinary container's bounded Container Manager metadata record must agree with its directory identifier before that identifier can ground exact matches in the other categories. Missing or unfamiliar metadata remains uncertain and locked. The internal metadata format is treated as optional evidence, with no fallback to guessed deletion authority. Shared group containers stay locked because their complete app membership is unknown. Installed or running apps sharing the first two identifier components retain related data. Apple system identifiers are retained.

Selectable targets require complete installed/cask/Library/process evidence and all content older than 30 days. The latest descendant modification date supplies the age floor. No-follow content inspection rejects nonowned files, hard links, symlinks, special nodes, advisory/record locks, user protection rules and sensitive filenames. Inspection is bounded per target and across the scan. Uncertain trees are not traversed merely to display an estimated size; the page says when size is unavailable.

The shared review sheet lists exact selected paths and the recoverability consequence. Cleanup deduplicates selection, enforces the configured `DeletionGuard` against live allocated size, then repeats full ownership/activity/Library inspection and compares inode, parent identity, every content node and timestamps before each Trash dispatch. Active process evidence is checked again immediately before removal. Containers are processed last so their metadata can continue grounding selected preference/support targets. Failures retain the affected data and remain visible in the shared results. `CleanupFileRemover.recoverable` is the only production removal operation. Trash bytes are accounted separately; freed bytes remain zero.

`SafetyChecker.validateForUninstallLeftover` admits only direct children of the known data roots, including Group Containers and Application Scripts. `validateForUninstallLeftoverTreeNode(_:within:)` first validates that root, then constrains descendant paths and checks every component for symlinks, sensitive names and user rules. Generic cleanup authority is unchanged. The injectable Library directory supports isolated fixture trees; production uses the current user Library.

Package tests construct real fixture Library/application trees and cask JSON. They cover every category, exact versus guessed ownership, installed/running/registered owners, shared-vendor and group retention, incomplete inventories, age, symlinks, locks, protected descendants, replaced identity, changed content, live-size caps, duplicate selection and removal failures. No real app data is removed during verification.

Apple documents why app groups require shared ownership treatment in [Configuring app groups](https://developer.apple.com/documentation/xcode/configuring-app-groups) and [Protecting local app data using containers on macOS](https://developer.apple.com/documentation/xcode/protecting-local-app-data-using-containers).

Verification (local, 2026-10-22): 82 affected package tests passed across six suites, including existing Uninstaller disposal and SafetyChecker tests. New feature sources/tests pass strict SwiftLint; shared SafetyChecker lint rule counts match the pre-change baseline. Full app-source compilation and a populated native `NSHostingView` capture succeeded. A real read-only scan returned 28 findings, zero selectable, with four inventory/access/budget diagnostics; the page showed each finding locked and disclosed the incomplete scan. This is partial inventory evidence, not proof that the Library is clean. No real app data was removed. Independent review was not requested.
